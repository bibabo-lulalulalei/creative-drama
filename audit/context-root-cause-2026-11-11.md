## 根因判断与排除

1. **事实工作范围没有执行入口。** 文档虽已要求按场工作，但只提供视频阶段的源投影工具；分镜仍依赖模型反复读取整集合同、数据卡和实现，自行提取当前场并计算源身份。压缩后摘要不足以替代原文，于是重新装载整包。
2. **创作输入和程序输出混在一个完整交付 JSON 中。** 原样例同时展示模型创意字段、allocate/pack 派生时间和哈希、最终审校字段；CLI 帮助缺少登记入口，促使模型为了开工先查清所有机器门。另一个真实陷阱是首次 pack 或设计变化会重建 SEG：若先填执行字段，之后可能被清掉。正确顺序需要由合同清楚表达。
3. **恢复没有接到可持续产出。** 长篇整集推演未及时保存为场次候选，恢复后再次从规则和实现开始。日志证明后面多轮只读不写，并非观察到字段错误后做必要排障。
4. **读取指令存在冲突。** `skill-details` 仍把普通规划确认/单项治理原文缺失扩大为整包治理；其他入口已说普通确认窄读。恢复成本因此可被不必要地放大。

静态工具并未逐轮膨胀：9 次 request shape 的 hash 相同，始终 16 个实际工具 schema（序列化共 48,666 字符）；299 个 deferred tool 只有名称，明确没有加载其 schema。skill listing 是 30 行、6,243 字符。不能把当前 Codex 的技能目录或 deferred 工具数当作此 Claude 会话的消耗。

宿主同时使用 high effort 并保留全部 thinking，是增长的放大因素；但最后一次区间仅 2,641 个去重 output tokens 就再次压缩，结合重复输入，不能只归因长输出。缓存也不释放上下文：例如日志行 1150 的 712 个 input tokens 加 165,688 个 cache-read tokens，仍接近 166k 上下文。没有以关闭压缩或修改全局模型参数代替 Skill 修复。
